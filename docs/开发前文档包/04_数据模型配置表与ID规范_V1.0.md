# 《洞天》数据模型、配置表与 ID 规范 V1.0

## 1. 目标

建立策划表、发布配置、服务端持久化和客户端展示之间的共同语言，确保：

- 同一个物品、行动、配方和解锁在所有层只有一个稳定 ID。
- 数值可热更新，但历史结算可复现。
- 资产变化可审计，余额可由账本核对。
- Numerical Master Sheet 能转成机器可读配置，而不是人工二次抄表。

## 2. 命名与 ID

### 2.1 稳定 ID

格式：`domain.tier.slug`，全小写 ASCII，单词用下划线；发布后永不复用。

示例：

```text
item.t1.qingling_herb
item.t2.spirit_marrow
action.t1.herb_baicao_valley
recipe.t1.qi_gathering_pill
equipment.t1.xuantie_sword
monster.t1.gray_wolf
dungeon.t1.xuantie_cavern
realm.qi.late
feature.queue.conditional
```

规则：

- ID 不使用中文、显示名称、数据库自增号或可变等级。
- 改名只改本地化 key，不改 ID。
- 删除内容标记 `deprecated=true`，不回收 ID。
- 数据库内部可用 UUID 主键，但业务引用必须保存稳定配置 ID。

### 2.2 实例 ID

- 玩家拥有的装备、队列项、秘境运行等实例使用 UUIDv7。
- 账本、事务和事件使用 UUIDv7，便于按时间排序。
- 幂等键由客户端生成 UUIDv7；服务端校验格式与账号归属。

### 2.3 本地化 key

```text
item.qingling_herb.name
item.qingling_herb.desc
action.herb_baicao_valley.name
error.queue_version_conflict
```

任何面向玩家的文本不得硬编码在服务端规则中。

## 3. 配置包结构

每个发布包为不可变目录：

```text
config/<config_version>/
  manifest.json
  realms.json
  feature_unlocks.json
  skills.json
  xp_curves.json
  items.json
  actions.json
  recipes.json
  tools.json
  equipment.json
  buffs.json
  monsters.json
  dungeons.json
  loot_tables.json
  breakthroughs.json
  cave_facilities.json
  tempering.json
  future/market.example.json  # 仅扩展锚点，不进入 MVP active manifest
  tutorials.json
  goals.json
  localization/zh-CN.json
```

`manifest.json` 必须包含：

```json
{
  "config_version": "2026.08.15.1",
  "schema_version": 1,
  "formula_version": 1,
  "created_at": "2026-08-15T00:00:00Z",
  "min_client_version": "0.1.0",
  "content_hash": "sha256:...",
  "previous_version": "2026.08.14.3"
}
```

## 4. 通用配置字段

所有内容表至少包含：

| 字段 | 类型 | 规则 |
|---|---|---|
| `id` | string | 全局或表内唯一稳定 ID |
| `name_key` | string | 本地化 key |
| `description_key` | string | 可选本地化 key |
| `enabled` | boolean | 禁用后不可新建，历史实例仍可结算 |
| `deprecated` | boolean | 保留兼容但不在新内容中使用 |
| `realm_required` | string | 最低境界阶段 ID |
| `feature_flag` | string? | 灰度或实验开关 |
| `sort_order` | integer | 显示顺序，不影响逻辑 |
| `tags` | string[] | 公式修正和筛选标签 |
| `source_note` | string | Numerical Sheet 工作表 / 行标签 |

## 5. 核心配置表

### 5.1 `realm_stage_config`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 如 `realm.qi.late` |
| `realm_group` | enum | `MORTAL/QI/FOUNDATION/...` |
| `stage_order` | int | 全局严格递增 |
| `cultivation_xp_start` | decimal | 累计起点 |
| `cultivation_xp_required` | decimal | 本段需要 |
| `queue_slots` | int | 1 / 2 / 3 |
| `medicine_slots` | int | 1 / 2 / 3 |
| `offline_cap_seconds` | int | 默认 36,000 |
| `unlock_bundle_id` | string | 成功进入时应用 |
| `scope` | enum | `MVP/MVP_ENDGAME/ANCHOR` |

### 5.2 `feature_unlock_config`

字段：`feature_id`、`visible_stage`、`usable_stage`、`mastery_stage`、`required_tutorial_ids`、`required_skill_id/level`、`feature_flag`、`locked_reason_key`。

服务端根据该表返回最终权限；客户端不得复制一套独立判断。

### 5.3 `item_config`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 稳定物品 ID |
| `category` | enum | HERB、ORE、MONSTER、PILL、EQUIPMENT 等 |
| `tier` | int | 内容阶级，不等于境界 |
| `stackable` | bool | 装备通常 false |
| `max_stack` | bigint | 需足够大，防止长期溢出 |
| `trade_policy` | enum | MVP 全部为 `NONE`；`SIMULATED/FUTURE_PLAYER` 仅预留枚举 |
| `npc_floor_price` | decimal? | 未来市场锚点；MVP 不导出、不使用 |
| `market_reference_price` | decimal? | 未来市场锚点；MVP 不导出、不使用 |
| `rarity` | enum | COMMON/UNCOMMON/RARE/EPIC |
| `overflow_policy` | enum | MATERIAL_STACK/TEMP_STORAGE |

### 5.4 `action_config`

字段：`id`、`skill_id?`、`base_duration_us`、`inputs[]`、`outputs[]`、`skill_xp`、`cultivation_xp`、`loot_table_id`、`allowed_queue_modes[]`、`required_tool_tag`、`modifier_tags[]`、`scope`。不属于百艺的修炼行动允许 `skill_id=null`，此时 `skill_xp` 必须为 0。

输出中的数量必须是整数或明确的 decimal 规则；随机物只通过掉落表引用。

基础无限修炼为必须存在的系统行动：

```json
{
  "id": "action.cultivation.qi",
  "name_key": "action.cultivation.qi.name",
  "description_key": "action.cultivation.qi.desc",
  "enabled": true,
  "deprecated": false,
  "realm_required": "realm.mortal.entry",
  "feature_flag": null,
  "sort_order": 10,
  "tags": ["cultivation", "fallback_eligible", "mvp"],
  "source_note": "Numerical Master Sheet V0.1 / 01_核心假设 A13:B13",
  "skill_id": null,
  "base_duration_us": "60000000",
  "inputs": [],
  "outputs": [],
  "skill_xp": "0.000000",
  "cultivation_xp": "4.500000",
  "loot_table_id": null,
  "allowed_queue_modes": ["DURATION", "INFINITE"],
  "required_tool_tag": null,
  "modifier_tags": ["cultivation"],
  "scope": "MVP"
}
```

配置中的微秒与 decimal 使用十进制字符串，加载时分别解析为 `bigint` 和 Decimal。基础值等价于每小时 270 修为；无物品输入、物品输出、百艺 XP 或随机掉落。它从新角色创建起可见可用，凡人、炼气和筑基均不失效，并作为新角色默认无限保底行动。

### 5.5 `recipe_config`

配方仍表现为行动，但单独表便于策划：`id`、`craft_skill_id`、`result_item_id/quantity`、`ingredients[]`、`base_duration_us`、`skill_xp`、`required_level`、`required_facility_id/level`、`scope`。

导出时生成或关联对应的 `action_config`，禁止服务端分别实现两套生产规则。

### 5.6 `equipment_config`

字段：`item_id`、`slot`、`attack`、`defense`、`hp`、`speed`、`power_index`、`equip_requirements`、`modifier_ids[]`、`temperable`、`max_temper_level`。

玩家装备实例额外保存：`instance_id`、`item_id`、`temper_level`、`bound`、`created_transaction_id`；基础属性不复制到实例，结算时由配置版本读取或使用快照。

### 5.7 `buff_config`

字段：`id`、`source_item_id`、`duration_seconds`、`slot_cost`、`stack_group`、`stack_rule`、`modifiers[]`、`applicable_tags[]`。

修正统一表示为：

```json
{
  "stat": "action_efficiency",
  "operation": "MULTIPLY",
  "value": 0.25,
  "tags": ["cultivation"]
}
```

修正计算顺序固定为：基础值 → 加法 → 同组乘法 → 全局乘法 → 软上限 → 舍入。

### 5.8 `monster_config` 与 `loot_table_config`

怪物字段：生命、攻击、防御、攻击间隔、技能脚本 ID、推荐战力、基础战斗时长、灵石、掉落表。

掉落项字段：`item_id`、`min_qty`、`max_qty`、`probability`、`rolls`、`pity_group?`。概率范围 `[0,1]`，每表导出时计算期望值并与数值母表核对。

### 5.9 `dungeon_config`

字段：`id`、`realm_required`、`opportunity_cost`、`entry_items[]`、`recommended_power`、`base_success_model`、`nodes[]`、`choice_timeout_seconds`、`default_route_id`、`reward_table_id`、`failure_reward_table_id`、`scope`。

节点字段：`node_id`、`type`、`monster_ids[]`、`choices[]`、`next_nodes[]`、`auto_resolve_policy`。

配置发布校验必须验证图可达、无无出口死环、默认路线完整。

### 5.10 `breakthrough_config`

字段：目标境界、累计修为、物品条件、货币成本、资产覆盖倍数、试炼 ID、成功率、成功解锁包、重复执行策略。

筑基基线：累计修为 24,100；筑基丹 1、灵髓 3、护脉丹 2、灵石 2,500；资产覆盖倍数 1；试炼 15 分钟；成功率 1。

### 5.11 `cave_facility_config`

字段：设施、等级、前置境界 / 前置等级、货币、材料、建造秒数、修正、scope。等级必须连续，成本与加成不可为负。

### 5.12 `tempering_config`

字段：目标等级、成功率、属性提升、淬炼石、灵石、同类装备、保护材料、失败结果、scope。MVP 可操作至 +6；+7～+10 只保留数据锚点。

### 5.13 `market_config`

市场整体延后。MVP 只保留 `feature.market` 稳定 ID，固定 `enabled=false`；`market_config` 不进入活动配置包，服务端不加载交易税、NPC 底价、报价或交易限额。

Numerical Master Sheet 中的市场数据保留为未来研究锚点。未来市场立项必须新增版本化 Schema 和迁移，不得改变现有库存、货币、账本与幂等语义。


### 6.1 角色版本

`characters.state_version` 每次权威写入递增。写请求可携带预期版本用于乐观并发控制；结算事务同时取得角色级数据库锁。

### 6.2 库存

可堆叠物品唯一键：`character_id + item_id`。数量使用 64 位有符号整数并设业务上限；任何更新必须满足 `quantity >= 0`。

库存同时保存 `reserved_quantity`，并满足 `0 <= reserved_quantity <= quantity`；所有可用性校验使用 `available_quantity = quantity - reserved_quantity`。预留必须关联队列周期、突破试炼或其他业务实例，超时释放只能通过幂等恢复事务完成。

`asset_reservations` 至少保存：业务类型 / 实例 ID、资产、数量、状态、创建 / 到期时间和释放 / 消耗事务 ID。状态为 `ACTIVE/CONSUMED/RELEASED/EXPIRED`；同一业务实例的活动预留建立唯一约束。

装备实例不可堆叠，所有权变更必须通过账本关联事务。

### 6.3 资产账本

每个业务事务写入平衡分录：

| 字段 | 说明 |
|---|---|
| `transaction_id` | 一次业务操作 |
| `entry_id` | 单条分录 |
| `character_id` | 资产主体 |
| `asset_type` / `asset_id` | 灵石、物品、机会等 |
| `delta` | 正负变化 |
| `balance_after` | 便于审计 |
| `reason_code` | 采集、配方、秘境、淬炼、突破等 |
| `reference_type/id` | 行动、秘境、装备、补偿 |
| `config_version` | 计算所用版本 |
| `created_at` | 服务端时间 |

禁止直接修改余额而不写账本。管理员修复也必须使用补偿事务。

## 7. Numerical Master Sheet → 配置流程

```text
数值策划修改黄色输入
→ 工作簿公式重算与平衡检查
→ 导出规范 CSV / JSON 中间表
→ Schema 校验
→ 交叉引用与公式一致性校验
→ 生成配置包与差异报告
→ 测试环境影子结算
→ 人工批准
→ 灰度发布
→ 监控 / 可回滚
```

源映射至少覆盖：

- `02_境界时间轴` → realm stages。
- `03_修为XP`、`04_百艺XP` → XP curves。
- `05_采集行动` → actions。
- `06_炼丹配方`、`07_炼器配方` → recipes。
- `08_工具梯度`、`09_装备梯度` → items / equipment。
- `10_怪物秘境` → monsters / dungeons / loot。
- `11_突破成本`、`12_洞府成本`、`13_淬炼成本` → progression configs。
- `14_市场基准价` → 未来市场锚点，不导出到 MVP 配置；`15_Faucet_Sink` → 非市场经济健康检查。

工作簿不是运行时依赖；服务端只加载已签名且校验通过的配置包。

## 8. 发布前自动校验

- ID 唯一、格式正确、引用存在、无循环依赖。
- 阶段、等级、洞府和淬炼梯度连续。
- 时间、成本、产出、概率和成功率在合法区间。
- 每个 MVP 物品至少有一个非市场来源；非终端材料至少有一个用途。
- 每个队列行动都有保底可达路径。
- 每个秘境图从入口可到成功或失败出口。
- 每个突破条件的材料在目标境界前可获得。
- 每个突破、洞府和关键配方材料在市场关闭时仍可由修炼、采集、生产、战斗、秘境、教程或目标奖励取得。
- 市场字段或来源不能进入 MVP active manifest，也不能被资源可达性校验视为有效来源。
- 配置包在一组黄金角色快照上重放，关键结果差异在批准范围内。

## 9. 迁移与兼容

- 新增字段必须有默认值；删除字段至少跨一个主版本保持读取兼容。
- 内容禁用不删除玩家已持有资产。
- 数值下调不追溯扣除历史收益。
- 物品合并或拆分通过一次性迁移和账本分录完成。
- 行动或秘境运行中遇到新配置时使用启动快照完成。
- 无法兼容的旧客户端由 `min_client_version` 阻止写操作，但允许读取维护说明。
