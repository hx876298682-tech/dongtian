# 《洞天》闭关、离线结算与秘境规则规格 V1.0

## 1. 目的与边界

本文是核心时间系统的实现规范，覆盖：

- 当前行动与闭关队列。
- 在线 / 离线统一结算。
- 材料不足、队列耗尽、配置更新、换装与跨设备冲突。
- 秘境机会、入场、自动战斗、路线选择、断线恢复与奖励结算。
- 与装备处理、淬炼、突破、洞府建造的并发关系。

本文不定义具体配方和掉率；数值来自配置与 Numerical Master Sheet。

## 2. 核心不变量

1. 服务端时间是唯一时间源；客户端时间只用于展示。
2. 在线与离线使用同一结算函数，离线不是折扣版独立公式。
3. 对同一角色的资产写操作串行化；同一时间不能出现两个权威结算者。
4. 任意请求重试都不能造成重复产出、重复扣除、负库存或重复突破。
5. 已完成的历史分段不因配置、装备或技能变化重算。
6. 新修正只从下一个尚未开始的完整行动周期生效；当前周期保持启动快照。
7. 闭关与主动秘境可以同时推进，但分别使用独立状态机与事务。
8. 所有资产变化都有来源、去向、数量、配置版本和关联事务。

## 3. 时间与精度

- 服务端存储 UTC 时间，精度为毫秒；行动计算使用整数微秒或高精度 decimal，禁止二进制浮点累计资产。
- 物品数量为整数；修为和 XP 允许配置定义的小数精度，入账时统一按向下取整或固定小数位处理。
- `effective_until = min(server_now, last_settled_at + offline_cap)`。
- 基础 `offline_cap = 10h`。在线心跳不增加特殊收益，只推进同一时钟。
- 短于 1 秒的反复请求不推进新的完整行动，但可返回最新状态。

## 4. 行动模型

每个闭关行动实例至少包含：

| 字段 | 含义 |
|---|---|
| `queue_entry_id` | 玩家队列项唯一 ID |
| `action_config_id` | 行动配置 ID |
| `mode` | `COUNT`、`DURATION`、`UNTIL_INVENTORY`、`INFINITE` |
| `target_value` | 数量、秒数或库存阈值 |
| `on_blocked` | `SKIP` 或 `FALLBACK`；MVP 不提供永久停机默认值 |
| `snapshot` | 行动开始时的速度、效率、工具、Buff、配置版本 |
| `reserved_inputs` | 当前未完成周期已预留、不可被其他操作使用的输入 |
| `completed_cycles` | 已完成完整周期数 |
| `progress_time_us` | 当前未完成周期累计有效时间 |
| `status` | `QUEUED`、`RUNNING`、`BLOCKED`、`DONE`、`DONE_INCOMPLETE`、`DONE_CONDITION_MET`、`CANCELLED` |

行动配置定义：基础耗时、输入、输出、XP、解锁条件、允许模式、随机表和修正标签。

## 5. 队列规则

### 5.1 槽位

| 境界 | 普通队列槽 | 条件模式 |
|---|---:|---|
| 凡人 | 1 | 无 |
| 炼气 | 2 | 无 |
| 筑基 | 3 | 简单条件 |

无限保底行动独立于普通槽位，必须始终存在。新账号默认设置为当前最高可用的“无限修炼”。玩家可改为允许无限执行的采集或普通历练。

### 5.2 保存

- 客户端提交完整目标队列、`expected_queue_version` 和 `idempotency_key`。
- 服务端校验解锁、槽位、参数、资源预览和版本。
- 版本一致时原子替换未开始的队列项，`queue_version + 1`。
- 当前正在运行的完整行动周期不被强行截断；新队列在当前周期完成后接管。
- 版本冲突返回 `QUEUE_VERSION_CONFLICT` 和最新队列，客户端要求玩家合并或覆盖。

### 5.3 取消与重排

- 已完成周期的输入和产出不可撤回。
- 当前未完成周期取消时释放预留输入；其累计进度清零，不产生输出。
- 若特殊行动在开始时永久扣除入场物，则取消规则由行动配置明确；MVP 普通生产只预留、不永久扣除当前周期输入。
- 重排只作用于未开始项。

### 5.4 阻塞后的队列项生命周期

- `on_blocked=SKIP`：记录未完成数量和原因，将该项标记为 `DONE_INCOMPLETE`，继续下一项；不会在同一队列中自动回头重试。
- `on_blocked=FALLBACK`：将该项保留为 `BLOCKED`，暂停其后的普通队列，开始无限保底；玩家补料并确认恢复，或保存新计划后再继续。
- 条件项进入时条件已经满足：标记 `DONE_CONDITION_MET`，直接继续下一项。
- 被跳过或取消的当前周期释放预留输入，未完成周期进度清零；摘要必须显示清零的时间，不把它计算为产出。
- 官方模板默认对生产项使用 `FALLBACK`，减少玩家误以为目标已经完成的风险。

## 6. 输入扣除与产出入账

### 6.1 普通生产行动

每个周期开始时，服务端先锁定库存并预留一整套输入。可用库存定义为 `quantity - reserved_quantity`；材料不足则周期不开始、不推进时间，并立即按阻塞规则处理。

每个完整周期结束时，在同一事务内：

1. 锁定角色结算状态和相关库存行。
2. 确认该周期预留仍有效。
3. 将预留输入转为永久扣除。
4. 计算确定性输出及随机输出。
5. 增加产物、修为、XP。
6. 写入经济账本与行动分段。
7. 提交事务。

周期进行中其他写操作不能装备、淬炼或消费预留输入。取消或技术恢复会释放预留；正常完成不会先释放再扣除，避免并发窗口。

### 6.2 随机性

- 每个行动周期的随机结果来自服务端 CSPRNG 或可审计伪随机种子。
- 种子由 `character_id + settlement_id + cycle_index + loot_table_version` 派生或安全记录。
- 重试同一结算使用相同结果，不重新抽取。
- 客户端不可提交随机结果。

### 6.3 批量结算优化

对确定性行动可按同快照批量计算完整周期数：

```text
cycles_by_time = floor(available_time / cycle_duration)
cycles_by_input = min over inputs floor(inventory / input_per_cycle)
cycles_by_target = remaining target cycles
completed = min(cycles_by_time, cycles_by_input, cycles_by_target)
```

历史完整周期可在一个事务内批量扣除和结算，不必逐周期写预留行；若结算区间末尾存在部分周期，只为该部分周期保留一套输入。随机掉落可使用确定性批量采样，但必须能在日志中重现总结果。出现库存阈值、Buff 到期或配置边界时必须切分区段。

## 7. 统一结算算法

### 7.1 触发点

结算在以下事件前自动执行：

- 登录 / 重连。
- 读取首页或行动状态达到刷新间隔。
- 保存队列、换装、使用丹药、淬炼、进入秘境、突破、洞府升级。
- 服务端后台安全检查或维护迁移。

### 7.2 算法

```text
settle(character, requested_now):
  lock character_settlement_state
  now = trusted_server_time(requested_now)
  start = last_settled_at
  end = min(now, start + current_offline_cap)
  remaining = end - start

  while remaining > 0:
    entry = running_entry or first_eligible_queue_entry or fallback
    if no entry:
      record IDLE_NO_ACTION
      break

    validate entry still unlocked and config exists
    if no active cycle snapshot:
      validate and reserve one cycle of inputs
      create snapshot
    boundary = earliest of:
      cycle completion
      target completion
      buff expiration
      config effective boundary
      inventory condition becoming true
      end

    advance to boundary
    if full cycle completes:
      atomic consume + produce + ledger
    if blocked:
      record reason and SKIP/FALLBACK
    if target complete:
      mark DONE and select next

  last_settled_at = end
  record capped_time = max(0, now - end)
  commit settlement summary
```

必须设置分段上限防止恶意配置造成无限循环。达到上限时保存安全检查点，返回 `SETTLEMENT_SEGMENT_LIMIT`，由后台继续处理；不得丢弃未结算时间。

## 8. 行动快照与配置版本

快照至少包含：

- `config_version`、行动基础耗时与配方版本。
- 技能等级及其速度 / 效率修正。
- 工具、洞府、丹药、装备和全局修正。
- 随机表版本与计算公式版本。
- 周期开始时间和预计结束时间。

规则：

- 技能升级、换工具、洞府升级、丹药启用在当前完整周期结束后生效。
- Buff 在周期中到期时，当前周期按开始快照完成；下周期不再包含 Buff。
- 热更配置只作用于热更生效时间之后新启动的周期。
- 破坏兼容的公式变更必须提升 `formula_version`，旧周期保留旧计算器直到完成或迁移。

## 9. 阻塞、保底与异常

| 原因 | 行为 | 摘要文案要求 |
|---|---|---|
| 材料不足 | 当前项 `BLOCKED`，按设置跳过或保底 | 缺少物品、数量、发生时间 |
| 条件已满足 | 不执行该项，标记 `DONE` | 目标库存已达到 |
| 行动被版本禁用 | 跳过并进入保底 | 配置已更新，未消耗资源 |
| 装备失效 | 使用新周期可用的合法配置；否则阻塞 | 缺少的工具 / 装备要求 |
| 背包容量 | MVP 采用可堆叠材料无硬容量；装备溢出进入临时收纳 | 收纳数量和处理入口 |
| 队列耗尽 | 执行无限保底 | 明确显示“已转为……” |
| 结算分段上限 | 保存检查点，后台续算 | 处理中，不允许重复操作 |
| 维护窗口 | 按可信服务端时间正常累积 | 不要求玩家维护时上线 |

禁止默认“因材料不足永久停止所有进度”。

## 10. 条件队列 MVP 语法

筑基只支持：

```text
执行 ACTION
直到 ITEM 库存 >= N

当 ITEM 库存 < N 时执行 ACTION

执行 ACTION 固定 N 次 / N 分钟
```

限制：

- 仅单一库存比较，运算符为 `<`、`>=`。
- 不支持价格条件、复合 AND/OR、自动交易或脚本。
- 条件每次进入队列项和每个完整周期后求值。
- 服务端校验目标物品确实可由该行动产出；不匹配时只警告，不阻止高级玩家保存。
- 提供“采到 N → 炼到 N → 无限修炼”官方模板。

## 11. 离线摘要

摘要至少包含：

- 结算起止时间、有效离线时长、超上限时长。
- 各行动实际执行时间、完整周期数、剩余周期进度。
- 获得与消耗的物品、修为、百艺 XP、灵石。
- 稀有掉落单独突出，但不逐周期刷屏。
- 队列切换点、阻塞点、保底行动启动点。
- 当前状态与建议入口。

同一 `settlement_id` 的摘要只展示一次强弹层，之后可在日志中查看。

## 12. 秘境机会规则

### 12.1 恢复

- `interval = 12h`，`cap = 6`，均来自配置。
- 机会自然累计，不按自然日重置。
- 达到上限后停止累计；封顶期间的溢出时间不储存，消耗后从该消耗事务时刻重新开始累计。
- 新手教学可赠送一次机会，但必须以独立账本来源记录。
- 查看页面不触发额外恢复；恢复由统一服务端时间计算。

精确状态保存 `current_count` 和 `recovery_anchor_at`。当 `current_count < cap`：

```text
gained = floor((now - recovery_anchor_at) / interval)
new_count = min(cap, current_count + gained)
new_anchor = recovery_anchor_at + gained * interval
```

当结果达到上限时，`recovery_anchor_at` 设为达到上限的精确时刻；封顶期间的额外时间不保存。消耗一次机会后，如果原本封顶，则以消耗事务的服务端时间作为新的恢复锚点。

### 12.2 入场事务

客户端提交：秘境 ID、配置版本、装备 / 策略预设 ID、路线首选项、幂等键。

服务端事务：

1. 先统一结算角色闭关进度。
2. 校验解锁、机会、入场物、装备合法性和是否已有运行中秘境。
3. 固化运行快照与随机种子。
4. 扣除一次机会和入场物。
5. 创建 `dungeon_run`，状态为 `ACTIVE`。
6. 提交并返回运行 ID。

一个角色同一时间只允许一个 `ACTIVE` 秘境。

## 13. 秘境运行状态机

```text
PREPARED
  → ACTIVE
      → WAITING_CHOICE
          → ACTIVE
              → COMPLETED
              → FAILED
      → EXPIRED_AUTO_RESOLVE
  → CANCELLED_BEFORE_COMMIT
```

- `PREPARED` 仅用于服务端事务内部，不向客户端形成可重复扣费窗口。
- 路线选择有配置化超时；超时采用玩家预设或默认安全路线，不要求实时在线。
- 战斗按固定 tick 或事件序列由服务端计算，客户端表现不影响结果。
- 玩家断线时运行继续或暂停等待选择；规则由节点配置决定。
- 失败仍返回已明确允许的阶段奖励；未获得奖励也要有原因。

## 14. 秘境配置与决策

MVP 每个正式秘境至少包含：

- 入场配置：武器、防具、饰品、最多 2 种战斗丹药、一个策略预设。
- 2～3 个节点：普通战斗、事件 / 风险选择、Boss 或出口。
- 至少一次有取舍的路线：安全低收益 vs 高风险高收益。
- 推荐战力和成功率仅为估算，不展示伪精确到小数的承诺；详情可解释主要差距。

成功率由装备战力、淬炼倍率、战斗专精、补给与推荐战力计算，最终受配置上下限约束。客户端显示区间，服务端使用精确值。

## 15. 秘境与闭关并发

- 秘境运行不占闭关队列槽，不暂停闭关。
- 进入秘境前先结算到入场时刻，固化秘境装备与丹药快照。
- 秘境期间闭关产出的物品不能中途自动注入已开始的秘境。
- 秘境获得的物品在运行结算事务后才能被闭关队列使用。
- 若秘境奖励使库存条件达成，下次闭关结算会正常跳过对应条件项。

## 16. 秘境退出、失败与断线

| 情况 | 机会 | 入场物 | 奖励 |
|---|---|---|---|
| 提交前取消 | 不扣 | 不扣 | 无 |
| 入场事务失败 | 不扣 | 不扣 | 无 |
| 已进入后主动放弃 | 已扣 | 已扣 | 仅已结算节点允许的奖励 |
| 战斗失败 | 已扣 | 已扣 | 按配置发失败 / 阶段奖励 |
| 客户端断线 | 不额外扣 | 不额外扣 | 重连恢复或取得已结算结果 |
| 服务端崩溃 | 依据已提交事务 | 依据已提交事务 | 用同一随机种子幂等恢复 |
| 配置热更 | 使用运行快照 | 不变 | 使用进入时版本完成 |

## 17. 资产操作、突破与洞府并发规则

- 所有写操作前先结算闭关至当前服务端时间。
- 装备、淬炼和其他资产消耗锁定相关物品行，且只能使用 `quantity - reserved_quantity`；提交后队列下个周期看到新库存。
- 市场整体延后，MVP 不实现报价、买卖、出售或 NPC 回收；未来接入时仍必须遵守先结算与预留不可消费规则。
- 突破在单事务内校验并扣除全部条件；成功后更新境界、解锁和队列容量。
- 洞府升级开始时扣除材料并创建建造任务；完成时加成从下一个行动周期生效。
- 两设备并发写入同一资产时只有先取得角色版本锁的一方成功，另一方收到版本冲突。

### 17.1 突破试炼状态机

```text
READY
→ TRIAL_ACTIVE
    → TRIAL_WAITING_CHOICE
        → TRIAL_ACTIVE
            → COMPLETED
            → FAILED_RECOVERABLE
```

- 创建试炼时校验并预留条件，但不立刻永久扣除；预留资产不可被淬炼或其他行动使用。
- 试炼完成事务再次校验预留，永久扣除材料与灵石，更新境界并应用解锁包。
- MVP 准备充分时最终突破成功率为 100%；`FAILED_RECOVERABLE` 只用于玩家主动放弃、配置非法或技术恢复，不销毁预留资产。
- 试炼断线按与秘境相同的运行恢复规则处理；重复开始返回现有试炼。
- 试炼最长占用和自动恢复策略由配置定义，默认 24 小时后释放预留并回到 `READY`。

## 18. 幂等与审计

关键写操作必须包含客户端生成的 UUIDv7 `idempotency_key`。服务端持久化：

```text
account_id
operation_type
idempotency_key
request_hash
response_snapshot
created_at
expires_at
```

相同键、相同请求返回原响应；相同键、不同请求返回 `IDEMPOTENCY_KEY_REUSED`。

必须审计：队列替换、结算、装备淬炼、秘境入场与结算、突破、洞府升级、管理员补偿、配置发布。

## 19. 关键边界用例

- 恰好在离线容量边界登录。
- 当前周期只差 1 微秒完成时换工具。
- 队列保存和登录结算同时发生。
- Buff 到期、周期完成和配置生效时间相同。
- 生产最后一次刚好耗尽输入。
- 条件库存被配方或淬炼消耗后重新低于阈值。
- 秘境入场扣款成功但响应丢失。
- 秘境等待选择期间跨配置版本。
- 筑基成功瞬间队列从 2 槽扩到 3 槽。
- 角色已经筑基但旧客户端再次提交突破。

以上用例必须进入自动化测试，不得只靠手工验证。
