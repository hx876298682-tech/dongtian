# 《洞天》离线结算事务与幂等 V1

## 结算记录

每次离线结算生成唯一 `settlement_id`，保存：

- 玩家 ID
- 请求开始时间、结束时间
- 实际结算秒数
- 参数版本
- 结算摘要哈希
- 状态：`pending`、`committed` 或 `rejected`

## 幂等规则

```text
if settlement_id already committed:
    return previous_summary
if settlement_id pending:
    resume or mark rejected before retry
else:
    calculate -> validate -> atomically commit -> mark committed
```

同一 `settlement_id` 重复领取不得重复增加修为、资源、掉落或保底计数器。提交必须同时写入库存、活动余数、随机计数器和结算记录；任一校验失败则整体回滚。

## 跨设备状态版本

离线状态必须同时持久化：秘境/地图保底计数器、随机数状态和 `state_revision`。提交采用比较并交换（CAS）：

```text
if request.expected_revision != player.state_revision:
    reject stale revision
else:
    atomically write inventory + pity + random_state
    state_revision += 1
```

重复 `settlement_id` 直接返回首次摘要，即使请求携带旧 revision 也不能再次改写保底或随机状态。跨设备并发的工程锁仍由数据库实现，但数值层的版本冲突结果已固定为拒绝，不允许“最后写入覆盖”。

## 时间回拨与重叠

- 服务器时间是唯一结算时间源，客户端时间只作为请求展示。
- 新请求开始时间早于上一次已提交结束时间时，只结算未覆盖区间；完全重叠请求返回 0 收益。
- 时间回拨、结束时间早于开始时间或跨度超过 24 小时的请求进入 `rejected`，不发放任何收益。

## 验证范围

V1 测试覆盖：重复 settlement ID、完全重叠区间、部分重叠区间、时间回拨、24 小时上限、事务失败不改库存、保底/随机状态持久化和 stale revision 拒绝。跨设备并发锁和真实数据库隔离级别需要在工程实现阶段接入，但数值结算契约先固定。
