# 《洞天》正式输入设计总草案 V1

> 状态：`proposal_v1`，仅供产品评审。本文不修改 `1.0.0-frozen` 参数、内容包、数据库 Schema、API 或 runtime；候选值不得直接进入 active release。

> 运行时说明：本文中的“主行动 + 后台生产”是历史设计/输入审计措辞。当前已批准并落地的 runtime 是 `global_single_slot_v1`：炼丹、炼器、功法研究和法宝研究占用唯一主动序列，灵田显式种植不占槽，legacy building job 不作为新玩法入口。

## 1. 目的

当前非 UI 工程底座已经完成，但 FI-01 至 FI-05 和随机事件缺少可发布的产品输入。本总草案把四份专项输入合并成一个评审入口：

- [FI-01/FI-02 草案](洞天正式输入设计草案_FI01_FI02.md)
- [FI-03/FI-05 草案](洞天正式输入设计草案_FI03_FI05.md)
- [FI-04/随机事件草案](洞天正式输入设计草案_FI04_随机事件.md)

产品确认后，工程才按“Schema/参数/内容 -> runtime/API/迁移 -> 测试/发布门禁”的顺序实施。

## 2. 不需要重新设计的已确认事实

- 主行动/单序列、灵田种植、战斗、掉落/保底、库存、装备手动成长、突破、离线结算、PostgreSQL、CAS/幂等和基础运营能力已有实现和回归；legacy 队列仅保留兼容边界。
- 普通地图已有总装备掉率、六档品质权重、品质倍率、槽位权重和手动升品成本；FI-01 主要缺正式内容对象和地图 binding。
- 高阶当前正式模式必须保持 `signature_only_v1`，不能用 synthetic fixture 或 proposal 数值开启 `full_v1`。
- 随机事件当前只有 opaque JSONB 持久化；在窗口、抽取、倍率、离线和 replay 语义获批前不接入 runtime。
- UI、CSS、图标素材生产不在本轮冻结范围；素材资源只有在内容包被批准后才进入 content manifest。

## 3. 推荐的首轮默认方案（仍需产品确认）

这些是为了减少评审分歧的建议，不是已经批准的正式值。

| 包 | 推荐默认 |
|---|---|
| FI-01 | 三张地图独立装备池；每个正权重品质覆盖六个实际部位；最小 90 个模板（24/30/36）；模板固定名称，图标和外观标签只用于展示/筛选；属性比例复用当前统一模板 |
| FI-02 | 清风总装备掉率先以 `5%` 做平衡候选；品质权重 `50/30/15/4/1/0`；720h 窗口、180h 清风支援时段；装备来源使用显式 binding，不隐式复用黑风参数 |
| FI-03 | 玩家显式开启；按服务器 1 小时周期；显式目标优先；重复件要求同模板、同部位、同品质且不能已装备/锁定；批次全有或全无；资源保留线和策略版本进入正式参数 |
| FI-05 | 独立 `POST /v1/collection/exchanges`；`starter` 与六个境界池分离；目标仅允许 0 星对象；每池独立印记；池满返回明确错误；旧全局印记采用保守迁入 `starter` 或 `legacy_unassigned`，二者须二选一 |
| FI-04 | 六境界各 8 个 `full_v1` 字段；开始时冻结 combat contract、玩家快照、Boss HP、参数版本和 seed；先用 `collected_p10/P25/P50` 三档做平衡验收 |
| 随机事件 | UTC 168h 窗口；互斥服务器抽取；每窗口只抽一次并持久化 `none` 结果；倍率只作用生产；离线按实际重叠秒数积分；统一采用完整窗口/实际 horizon 截断公式，先修正文档与验证器口径再开发 |

## 4. 必须由产品拍板的最小决策集

### 4.1 内容和经济

1. FI-01 是否接受 90 个模板下限，还是首发要求每个品质/部位至少两个外观变体。
2. 名称是模板固定名称还是实例随机名称；图标、外观标签是否首发进入 Schema。
3. 清风掉率选择 3%、5% 还是 7%；品质权重是否定义为合计 100 的百分比。
4. 清风复用普通地图模板子集，还是建立独立装备池；传说 1% 是否制作六个传说模板。
5. 30/90 天的仓库峰值、六部位成型率、出口和突破资源作为何种验收上限。

### 4.2 自动升品和兑换

1. 自动升品周期是 1 小时、每日还是离线结算批次；是否允许部分成功。
2. 目标和重复件是否必须同模板/同部位/同品质；装备中、锁定实例能否被消费。
3. 升品后洗练次数、词条、锁定槽、觉醒等级如何继承。
4. 兑换成本是否统一 10 个印记；目标是 0 星还是未满 10 星。
5. 首发池和六个境界池的解锁条件、是否跨池消费、池满行为。
6. 旧全局 `collection_marks` 选择迁入 `starter` 还是进入不可消费的 `legacy_unassigned`。

### 4.3 高阶和随机事件

1. 六境界 48 个字段的正式数值、技能 magnitude 单位、同秒技能顺序、DoT/控制/压制叠加规则。
2. 高阶目标通关时间、自然失败率、丹药 P95 和 720/2160/6480h 净供给门槛。
3. 随机事件是否采用 UTC 周窗口；服务器随机源或确定性派生算法、密钥版本和回放保留期。
4. 随机事件公式采用完整窗口基线 `1.0013095238...`，还是 2160h 截断基线 `1.0012222222...`；非整窗如何计入。
5. 随机事件激活时旧 opaque 状态如何迁移；默认建议从 `lastSettledAt` 所在窗口初始化为 `none`，不补发历史倍率。

## 5. 产品批准后的工程顺序

1. 形成带 owner、approver、approved_at、source、decision record 的正式输入包。
2. 更新内容 Schema、参数 CSV 和生成产物；重算 parameter/content hash 和 manifest。
3. 实现 FI-01/FI-02 内容 binding 与清风运行时；实现 FI-03 mutation/API；实现 FI-05 分池状态、迁移和兑换；实现 FI-04 full_v1；最后实现随机事件 runtime。
4. 补 Memory/PostgreSQL、事务、CAS、幂等、replay、跨进程恢复和审计测试。
5. 执行 `npm test`、typecheck、build、release audit、真实 PostgreSQL integration、Ruby 专项审计和固定 seed 平衡报告。
6. 只有专项门禁全部通过，才创建新 config/content version 并进入 canary；UI 最后接入。

## 6. 当前发布结论

当前 release 仍为 `1.0.0-frozen` / `signature_only_v1`，整体状态仍是 `partial / infrastructure_and_feature_gaps`。本总草案完成的是产品决策准备，不代表任何 FI 项已关闭；在产品批准前，工程必须继续保持 fail-closed。
