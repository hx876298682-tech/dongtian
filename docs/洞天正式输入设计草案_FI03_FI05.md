## 2. 产品冻结前的共同原则

- 数值、对象池和策略都必须进入版本化输入包；不能从其他地图、其他境界、测试 fixture 或 proposal 文档复制。
- 写操作必须由服务端根据持久化状态决定目标、消耗和结果；客户端只能提交意图、候选目标和 expected revision，不能提交最终资源余额或升品结果。
- 任一校验失败、资源不足、目标失效或 CAS 冲突，都不应产生部分状态变化。
- 每一次成功 mutation 都要记录前后 revision、config version、请求指纹、资源 ledger、对象 ID 和可重放响应。
- UI 不参与规则计算。先冻结输入并完成领域/API/数据库验收，移动端 UI 最后接入。

## 3. FI-03 自动升品调度策略包（候选方案）

### 3.1 不能重复发明的现有参数

下列值已经在当前冻结 CSV 中，不能在自动升品草案中改写：

| 参数 | 当前值 | 事实 |
| --- | ---: | --- |
| `loot.equipment.promotion.duplicate_required` | 1 | 手动/提案共享的每次升品重复件数量 |
| `loot.equipment.promotion.success_chance` | 100 | 升品确定成功 |
| `loot.equipment.promotion.enhancement_preserved` | 1 | 强化等级保留 |
| 普通 -> 精良 | 500 灵石、5 千年灵药、10 天外陨铁 | 已冻结 |
| 精良 -> 稀有 | 1,000 灵石、10 千年灵药、20 天外陨铁 | 已冻结 |
| 稀有 -> 史诗 | 2,000 灵石、20 千年灵药、40 天外陨铁 | 已冻结 |
| 史诗 -> 传说 | 4,000 灵石、40 千年灵药、80 天外陨铁 | 已冻结 |
| 传说 -> 仙器 | 8,000 灵石、80 千年灵药、80 天外陨铁 | 已冻结 |

仍缺正式参数 `schedule.equipment.auto_promotion.enabled`。即使补上该 flag，也不能替代下列调度语义。

### 3.2 候选触发方式

建议采用“玩家显式开启 + 每个结算周期最多执行一次”的模型：

- 玩家在装备管理中提交自动升品策略；启用状态是服务端持久化的策略，而不是每次离线结算临时传入的布尔值。
- 自动升品在一次玩家状态结算成功后运行，使用该结算结束时的装备、库存和资源快照。
- 每个调度周期以 `floor(server_time / period_seconds)` 计算 `cycleId`；周期长度暂定为 `3600` 秒，仅作为候选值，需产品确认是否按 1 小时、离线结算批次或每日执行。
- 周期内没有满足条件的目标时记录一次 `skipped` 摘要；不消耗资源、不增加 revision，还是增加一次策略审计 revision，需要产品明确。建议不产生玩家 mutation，只写调度审计。

候选新增参数（不代表已加入 CSV）：

```text
schedule.equipment.auto_promotion.enabled
schedule.equipment.auto_promotion.period_seconds
schedule.equipment.auto_promotion.max_operations_per_cycle
schedule.equipment.auto_promotion.resource_reserve.spirit_stone
schedule.equipment.auto_promotion.resource_reserve.millennium_herb
schedule.equipment.auto_promotion.resource_reserve.meteor_iron
```

### 3.3 候选目标选择与重复件消费

每个升品 operation 由服务端形成 canonical command：

```json
{
  "targetInstanceId": "<owned canonical equipment instance>",
  "fromQuality": "fine",
  "toQuality": "rare",
  "duplicateInstanceIds": ["<same template, same slot, same quality>"],
  "resourceCost": {
    "spirit_stone": 1000,
    "millennium_herb": 10,
    "meteor_iron": 20
  }
}
```

候选规则：

- 目标必须属于当前玩家、未达到仙器、品质迁移必须是相邻档位。
- 重复件必须与目标 `templateId`、实际 slot、当前 quality 完全一致；不允许仅凭“同部位”吞噬，避免不同装备模板被误消费。
- 目标本身不能同时出现在重复件列表中。重复件不得是已装备实例、已锁定实例或已被另一操作预留的实例；若产品允许消费已装备/已锁定实例，必须单独冻结解除装备和解锁行为。
- 建议按 `createdAt ASC, instanceId ASC` 选择重复件，以最早获得的非核心实例优先；目标选择则按以下优先级稳定排序：品质更高优先、已装备优先、强化等级更高优先、`createdAt ASC`、`instanceId ASC`。其中“已装备优先”会直接改变玩家战斗构筑，建议改为“已装备不自动作为目标”，由产品确认。
- 推荐的保守候选是：自动升品只处理玩家显式列入策略的 `targetInstanceId` 或 slot/quality 白名单，不让服务器在全库存中猜测核心装备。

### 3.4 执行顺序与批量边界

候选执行顺序如下：

1. 先按显式目标优先级，再按 `slot` 固定顺序 `weapon, armor_1, armor_2, armor_3, armor_4, accessory`。
2. 同一 slot 按品质低到高，优先只做能完成的相邻升品。
3. 同一品质和 slot 按目标的稳定排序键执行。
4. `max_operations_per_cycle` 限制本周期 operation 数；超过上限的目标保持未处理并进入摘要。

建议一个周期使用一个事务、全批次原子提交：任一 operation 的重复件、资源、实例状态或目标策略校验失败，则整个周期不消费任何装备和资源，并返回可诊断的 `blocked` 原因。若产品需要“前 N 个成功、剩余跳过”，必须另行冻结部分提交、每 operation revision 和失败恢复语义，不能由工程自行推断。

### 3.5 资源预留

候选采用“保留线 + 本周期成本”两层判断：

```text
available = amount - reservedAmount
spendable = available - policyReserve
```

- `policyReserve` 是玩家策略或正式参数中的最低保留量；不能用请求 body 临时覆盖正式策略。
- 执行前先计算整个候选批次的总成本、重复件数和每个资源的最终余额；任何一项不足就整批跳过。
- 升品不是建筑队列，不应把成本写成未来可释放的 `reservedAmount`；成功提交时一次性扣除，失败不扣除。
- 资源成本和重复件消费必须出现在同一事务 ledger 中，并检查非负与容量 invariant。

### 3.6 状态继承候选

现有冻结事实只有强化等级保留。建议产品评审以下明确规则：

| 状态 | 候选规则 | 当前事实/风险 |
| --- | --- | --- |
| 强化等级 | 保留 | 已有 `enhancement_preserved=1` |
| 词条值与槽位 | 保留原对象，重新写入品质预算/品质倍率 | 当前 `EquipmentInstance` 有 `affixes`，但没有正式“预算重算”契约 |
| 锁定槽 | 保留索引，但若新品质槽位上限不足则整批阻断 | 需要 Schema/门禁明确 |
| 洗练次数 | 保留或重置必须二选一 | 当前实例没有持久化洗练次数字段 |
| 觉醒等级 | 建议保留，或明确升品后重置和返还 | 当前手动升品代码未定义觉醒继承规则 |
| 装备中状态 | 建议目标可升品但重复件不可为装备中 | 需避免升品期间战斗快照不一致 |

若产品选择“保留洗练/觉醒”，工程需先补充实例字段、Schema、数据库列/JSON 契约和 replay；不能仅靠 `affixes` 里的临时 key 代替正式字段。

### 3.7 候选 API/DTO

建议新增独立 route，不扩展现有只读长期投影：

```text
POST /v1/equipment/auto-promotion/cycles
```

请求（候选）：

```json
{
  "expectedRevision": 42,
  "cycleId": "2026-08-26T10:00:00Z/3600",
  "enabled": true,
  "targets": [
    { "instanceId": "...", "maxPromotions": 1 }
  ],
  "policyVersion": "<config version>"
}
```

正式策略更适合单独用 `PUT /v1/equipment/auto-promotion/policy` 保存，周期 route 只接受服务端已保存策略和 `cycleId`。上面的合并 DTO 仅用于讨论，不能直接实现。

响应至少应包含：`cycleId`、`status`、`operations[]`、每项的目标/重复件/前后品质/资源成本、`skipped[]`、总资源 ledger、`beforeRevision`、`afterRevision`、`configVersion` 和 `summaryHash`。

### 3.8 幂等、CAS、审计和回放

- canonical action key 候选为 `playerId:auto-promotion:<cycleId>:<policyFingerprint>`；相同 key 且请求指纹一致时返回首次响应。
- 同一 `cycleId` 的不同目标、策略或 config version 必须返回 `DUPLICATE_REQUEST`，不能复用旧结果。
- 事务在玩家行锁后再次检查 action replay，再检查 expected revision，再计算和写入草稿，最后写 action response、audit 和 equipment ledger。
- CAS 失败返回 `STALE_REVISION`；不能重算并自动覆盖玩家新状态。
- 审计事件建议为 `equipment_auto_promotion_cycle`，payload 包含策略指纹、周期、目标实例、重复实例、资源前后余额、跳过原因、前后 revision 和配置版本。
- replay 读取持久化响应，不根据当前参数重新计算历史结果；历史装备对象 ID、消耗和资源 ledger 必须可验证。

### 3.9 FI-03 产品签字条件

产品需要在输入包中补齐：启用、周期、批次上限、目标选择、重复件选择、执行顺序、资源保留、继承、部分失败策略、策略版本和审计字段。工程随后才能实现 route/DTO、实例消费、事务/CAS、跨进程幂等和测试。

## 4. FI-05 法宝收藏印记兑换协议（候选方案）

### 4.1 现有可引用事实与提案边界

当前法宝成长文档给出的候选事实是：法宝最高 10 星；重复掉落在满星后转为 1 个收藏印记；累计 10 个印记兑换 1 件当前未拥有法宝；高阶各境界有独立 12 件扩展池且不混抽。但该文档整体状态仍为 `proposal_v1`，不能直接作为正式兑换契约。

当前冻结参数已有 `growth.treasure.max_stars=10`、`growth.treasure.duplicate_copies_per_star=1` 及首发/扩展对象的若干效果参数；没有“兑换成本、池选择、旧全局印记迁移”的正式参数或 route。

### 4.2 候选对象池模型

建议将兑换池定义为稳定的 `poolId`，而不是由客户端传入境界名称后在服务端临时映射：

| poolId 候选 | 开启条件候选 | 对象范围 |
| --- | --- | --- |
| `starter` | 首发秘境解锁 | 6 件首发法宝 |
| `nascent_soul` | 元婴远征解锁 | 元婴 12 件扩展对象 |
| `divine_transformation` | 化神远征解锁 | 化神 12 件扩展对象 |
| `void_refining` | 炼虚远征解锁 | 炼虚 12 件扩展对象 |
| `body_unity` | 合体远征解锁 | 合体 12 件扩展对象 |
| `great_vehicle` | 大乘远征解锁 | 大乘 12 件扩展对象 |
| `tribulation` | 渡劫远征解锁 | 渡劫 12 件扩展对象 |

每个池的印记余额必须独立；兑换不得跨池扣除或兑换。扩展池之间不得因为同名原型、相同五行或客户端伪造 `realmId` 而混池。

### 4.3 候选 route 与 DTO

建议新增：

```text
POST /v1/collection/exchanges
```

候选请求：

```json
{
  "poolId": "starter",
  "targetTreasureId": "qing_lian_lamp",
  "expectedRevision": 42
}
```

`Idempotency-Key` 必填；服务端从正式配置读取 `marksCost`，不接受客户端传入成本。建议将 `poolId`、`targetTreasureId` 和 `expectedRevision` 作为严格字段，拒绝未知字段和 snake_case 别名。

候选响应：

```json
{
  "poolId": "starter",
  "targetTreasureId": "qing_lian_lamp",
  "marksSpent": 10,
  "fromStars": 0,
  "toStars": 1,
  "marksRemaining": 0,
  "collectionState": {},
  "beforeRevision": 42,
  "afterRevision": 43,
  "configVersion": "1.0.0-frozen",
  "summaryHash": "..."
}
```

响应结构中的具体字段名、是否返回全量 collection state、是否把兑换写成新掉落事件，须在正式 API 契约中冻结。

### 4.4 目标选择与池满行为

推荐候选规则：

- `targetTreasureId` 必须属于请求的 `poolId`，且对象状态 `stars == 0`；兑换是“补齐未拥有对象”，不直接把已有 1 星对象再升星。
- 目标对象必须已被该玩家可用的境界池解锁；服务端不得仅信任客户端的 `poolId`。
- 兑换本身给目标 1 星，不消耗重复 copy，不触发掉落 pity，不增加额外印记。
- 兑换前检查当前池印记余额至少为 `marksCost`，且目标未拥有；余额不足、目标不属于池、池未解锁均整笔拒绝。
- 若当前池所有对象均已拥有（或按产品选择均已满星），返回明确的 `COLLECTION_POOL_COMPLETE`，不扣印记、不改变 revision；不要自动把印记转到其他池。
- 若池中有对象已拥有但未满星，推荐仍允许兑换其他未拥有对象；“优先补 0 星”与“允许补未满星”必须作为一个明确的目标口径冻结。

这里的“10 个印记”和“只兑换 0 星对象”都是当前 proposal 的候选，不是现行正式参数。建议将成本登记为 `growth.treasure.exchange.marks_cost.<poolId>`，并要求 `frozen_v1` + provenance 后才可启用。

### 4.5 余额与数据库模型候选

现有全局 `collection_marks` 不能安全地直接拆到多个境界池，因为历史记录没有记录印记来源池。推荐新增按池持久化结构，例如：

```text
collection_pool_state
  player_id       uuid
  pool_id         text
  marks           bigint >= 0
  state_revision  bigint >= 0
  primary key (player_id, pool_id)
```

并把 `collection_marks` 明确标为 `legacy_unassigned_marks`，或保留一份不可消费的迁移余额。不要把旧全局数值复制到每一个池，也不要按当前境界、当前法宝星级或对象数量猜测分配。

迁移必须先由产品在以下方案中签字：

| 方案 | 处理 | 风险 |
| --- | --- | --- |
| A（推荐保守） | 旧全局余额全部迁入 `starter`，明确公告只适用于首发池；高阶池从迁移后新产生的分池印记开始 | 可能把历史高阶来源余额归入首发池，但不会复制或凭空增加余额 |
| B（最严格） | 旧余额进入 `legacy_unassigned`，在映射规则冻结前不可兑换 | 用户暂时无法使用旧余额，但不会错误归属 |
| C（不接受） | 按当前境界、星级或对象数量自动拆分 | 无来源证据，结果不可审计，禁止实现 |

无论选择 A 或 B，迁移应是一次性、可回放、带旧值/新值 hash 的数据迁移；发现 legacy 数据不符合非负约束时 fail-closed。迁移完成后新掉落必须直接写对应 `poolId`，不能继续写全局 `collection_marks`。

### 4.6 幂等、CAS、事务与审计

- canonical action key 候选为 `playerId:collection-exchange:<poolId>:<targetTreasureId>:<idempotencyKey>`，请求 fingerprint 必须包含 pool、target、expected revision 和 config version。
- 相同 key 且 fingerprint 一致返回首次响应；同 key 不同目标或池返回 `DUPLICATE_REQUEST`，不读取客户端新请求作为覆盖。
- 事务取得玩家行锁后重查 action replay，再校验 expected revision、池归属、解锁条件、目标星级、印记余额和 `max_stars`，最后原子扣池余额并写目标 1 星。
- 成功兑换递增玩家 `state_revision`，写 `collection_exchange` audit 和收藏事件；失败不递增 revision、不产生部分扣款。
- 审计 payload 至少包含 pool、target、marks before/after、stars before/after、cost、migration source（若使用 legacy 余额）、config version、request fingerprint 和前后 revision。
- replay 只返回持久化首次响应；不按当前对象池或当前成本重算历史兑换。

### 4.7 FI-05 产品签字条件

正式输入必须冻结：route 和 DTO、兑换成本、首发/高阶 poolId、池解锁条件、目标 0 星或未满星口径、池满错误和印记去向、旧全局余额迁移方案、每个掉落来源写入哪个池、幂等 fingerprint、CAS 失败和审计字段。工程才能扩展 `CollectionState`/SQL、实现 mutation 和迁移，并补 Memory/PostgreSQL/HTTP/replay 测试。

| 能力 | 必须有的测试 | 发布前证据 |
| --- | --- | --- |
| 自动升品成功 | 单周期一到多次升品、资源和重复件守恒、继承规则 | Memory + PostgreSQL transaction |
| 自动升品阻断 | 目标失效、重复件不足、资源保留线、池/周期未解锁 | 错误码和无状态变化断言 |
| 自动升品并发 | 相同周期重复、不同策略同周期、同 revision 并发 | 1 次成功，其余 replay/duplicate/stale |
| 自动升品回放 | 跨进程读取原响应和 ledger | response hash 一致 |
| 兑换成功 | 每池、每目标、成本扣减、1 星写入 | Memory + PostgreSQL |
| 兑换池隔离 | starter 与各高阶池交叉 target/pool、未解锁池 | fail-closed，无跨池余额变化 |
| 兑换池满 | 全部目标已拥有/满星、余额充足 | 明确错误，不扣款 |
| 兑换迁移 | 旧全局余额 A/B 方案、重复迁移、脏数据 | 一次性 hash、可重放、无复制余额 |
| 兑换 replay | 相同/不同 payload、跨进程重启 | 首次响应稳定，错误请求不覆盖 |

## 6. 产品评审清单

### FI-03 必答

- 周期是 1 小时、每日、离线结算批次，还是其他窗口？
- 自动升品是全库存排序还是显式目标？装备中/锁定实例能否被目标或重复件消费？
- 同模板、同部位、同品质的重复件口径是否确认？
- 批次是全有或全无，还是允许部分成功？
- 灵石、千年灵药、天外陨铁各自的保留线是多少，按账号策略还是正式参数？
- 洗练次数、词条、锁定槽、觉醒等级如何继承？当前实例缺失的字段是否补 Schema？
- 周期重复时是否只返回 replay，还是允许同周期追加新目标？

### FI-05 必答

- route、DTO、`poolId` 和目标字段是否接受本草案候选命名？
- 成本是 10 个印记还是按池配置？是否只允许兑换 0 星对象？
- 首发池和六个境界池的解锁条件、掉落归属和池满行为是什么？
- 旧全局 `collection_marks` 采用 A（迁入 starter）还是 B（legacy 冻结），谁批准迁移？
- 兑换是否增加新星级、是否产生掉落 pity/重复 balance 变化？
- 审计是否需要展示用户可读的迁移来源和兑换历史？
