# 《洞天》正式输入包缺口清单与验收模板 V1

## 1. 用途与边界

本文档把当前阻断非 UI 正式发布、且不能由工程自行猜测的产品输入整理为可交付、可校验、可追溯的模板。它不是参数提案，不给出缺失数值，也不能作为正式输入本身。

以下内容一律不能替代正式输入：`proposal_v1` 文档、测试 fixture、synthetic 数据、UI 静态数据、从其他地图或境界复制的参数、仅有口头结论但没有来源记录的值。

正式输入必须同时满足：

1. 字段完整且符合当前 Schema；若当前 Schema 尚无字段，必须先由产品冻结语义，再由工程扩展 Schema 和验证器。
2. 每个参数有 `status=frozen_v1` 和非空 `source`；高阶 `full_v1` 的来源不得包含 `proposal`、`synthetic`、`fixture` 或 `test`。
3. 参数包和内容包分别重算 SHA-256，manifest 的版本与两个 hash 一致。
4. 对应运行时门禁、发布门禁和自动化验证全部通过。
5. 待产品决策项有明确结论、责任人、批准时间和依据链接，不能留空后进入 canary/active。

## 4. 通用参数行模板

所有新增或修改参数必须按权威 CSV 的 12 列提交：

| CSV 列 | 类型/约束 | 验收要求 |
| --- | --- | --- |
| `parameter_id` | 非空唯一字符串 | 与下文精确 ID 一致；不得建立别名绕过契约 |
| `domain` | 非空字符串 | 与参数所属领域一致 |
| `parameter_name` | 非空字符串 | 可读且能唯一解释参数 |
| `value` | 按字段类型 | 不在本模板预填；由产品正式冻结 |
| `unit` | 非空字符串 | 概率、秒、资源等单位明确 |
| `value_type` | 枚举/类型标签 | 与运行时消费类型一致 |
| `status` | 字符串 | 必须为 `frozen_v1` |
| `source` | 非空字符串 | 指向批准的设计/平衡依据；不得是 proposal 或测试来源 |
| `reference_source` | 字符串 | 有外部或历史依据时填写 |
| `formula_or_rule` | 字符串 | 派生值必须给出可复算规则 |
| `rounding` | 字符串 | 数值涉及舍入时必须明确 |
| `notes` | 字符串 | 记录适用范围、版本和异常规则 |

每次变更必须生成新 `config_version`，重新生成 `demo/src/game/frozen-parameters.ts` 和 `demo/src/game/parameter-manifest.ts`，不得直接手改生成文件。

### 5.4 尚未进入 Runtime Schema 的正式内容字段

首发内容规格还要求名称池、图标、外观标签和套用的属性模板，但当前 `EquipmentTemplate` 没有对应字段。产品必须先提交以下语义决策，工程才能确定 JSON key 和验证器；本表故意不虚构字段名：

| 待冻结语义 | 建议数据形态，仅用于评审 | 必须回答的问题 |
| --- | --- | --- |
| 名称池 | 稳定 ID 与显示名的对象数组 | 名称是模板级固定还是实例随机；是否按地图/品质/部位隔离 |
| 图标引用 | 资源 ID 字符串 | 资源清单、缺失策略、版本和 hash 如何绑定 |
| 外观标签 | 稳定字符串或枚举数组 | 标签字典、唯一性、是否参与掉落/属性逻辑 |
| 属性模板引用 | 参数/内容对象 ID | 当前攻击/防御/生命比例如何映射六部位；模板能否跨品质复用 |

在这些 key 和约束进入 `content-schema.ts` 之前，只补任意自定义 JSON 字段不能计为验收完成。

### 5.5 FI-01 hash 与门禁

提交人填写：

```text
content_version: <待填>
source_document: <待填>
approved_by: <待填>
approved_at: <待填>
content_sha256: <由 hashContent 生成，不手填猜测值>
parameter_sha256: <对应新参数包 hash>
```

必须通过：

- `validateContentPackage`：ID、枚举、参数引用、manifest 与 canonical content hash 全部合法。
- `diagnoseContentReachability`：可达地图、配方和已绑定装备无 `content_pending`。
- `diagnoseMapEquipmentReleaseReadiness`：三地图 binding、正权重品质、三槽位类别和出口策略无诊断。
- `validateOrdinaryMapEquipmentRelease`：返回成功，不得仅以应用能启动代替该严格门禁。
- 额外验收：六个实际部位均有可达模板。`diagnoseMapEquipmentReleaseReadiness` 现在同时检查 `weapon`、`armor_1`、`armor_2`、`armor_3`、`armor_4`、`accessory` 六个实际槽位；缺任一槽位都会返回 `MISSING_TEMPLATE_FOR_SLOT`，因此当前内容仍不能签字。

## 7. FI-03 自动升品调度策略包

### 7.1 参数现状更正

以下参数已经存在且为 `frozen_v1`，不是缺口：

- `loot.equipment.promotion.duplicate_required`
- `loot.equipment.promotion.success_chance`
- `loot.equipment.promotion.enhancement_preserved`
- 五段 `loot.equipment.promotion.{transition}.{spirit_stone|millennium_herb|meteor_iron}_cost`

当前唯一由代码直接诊断为缺失的启用参数是：

| `parameter_id` | 类型/当前代码要求 | provenance |
| --- | --- | --- |
| `schedule.equipment.auto_promotion.enabled` | number/boolean flag；当前 `validatePromotion` 只接受数值 `1` 表示启用 | `status=frozen_v1` 且 `source` 非空 |

### 7.2 未冻结的调度契约

只添加 enable flag 仍不能构成正式自动升品产品能力。产品必须冻结：

| 决策项 | 必须明确的契约 |
| --- | --- |
| 目标选择 | 对哪件 canonical 装备、哪个部位、哪个当前品质发起升品 |
| 重复件选择 | 必须同模板还是只需同部位/同品质；锁定、装备中或待售实例能否消费 |
| 执行顺序 | 多部位、多品质同时满足时的稳定排序和批量上限 |
| 资源预留 | 突破材料、丹药、灵石的最低保留线；不足时跳过还是终止批次 |
| 状态继承 | 强化已明确保留；洗练次数、词条、锁定槽、觉醒等级如何处理 |
| 幂等与并发 | 调度周期 ID、重复请求、CAS 冲突、部分批次失败的原子性 |
| 可观测性 | 审计事件、资源 ledger、被消费 instance ID、结果摘要字段 |

其中“洗练次数等继承规则”只存在于 `proposal_v1` 文档，不能直接计作 frozen provenance。

### 7.3 FI-03 门禁

- `validatePromotion` 对启用参数、重复件、100% 成功率、强化继承和每段资源成本无诊断。
- 产品冻结上述调度契约后，工程必须实现权威 mutation/API、事务、CAS、幂等、审计和自动化测试；当前长期消费模块只是只读规划切片，不能作为正式自动执行能力。
- 至少覆盖成功、资源不足、重复件不足、并发冲突、重复请求 replay、跨进程恢复和资源守恒。
- 所有新增策略参数进入同一 parameter hash；不得用请求 body 临时传入正式策略绕开 release。

## 8. FI-04 六境界 `full_v1` 高阶战斗包

### 8.1 模式字段

当前参数：

```text
dungeon.high_tier.combat_mode = signature_only_v1
```

只有在以下 48 个字段全部完成并通过结构、provenance 和平衡验收后，才能在新参数版本中将其改为 `full_v1`。不能先切模式再补字段。

### 8.2 六境界前缀

以下每个前缀都必须提交完整 8 字段：

```text
dungeon.high_tier.nascent_soul
dungeon.high_tier.divine_transformation
dungeon.high_tier.void_refining
dungeon.high_tier.body_unity
dungeon.high_tier.great_vehicle
dungeon.high_tier.tribulation
```

### 8.3 每境界精确字段模板

| 后缀 | `value` 类型 | 结构约束 | 单行 provenance |
| --- | --- | --- | --- |
| `.boss_attack` | finite number | `>=0` | `status=frozen_v1`；正式来源非空 |
| `.boss_defence` | finite number | `>=0` | 同上 |
| `.boss_accuracy` | finite number | `>=0` | 同上 |
| `.boss_attack_interval_seconds` | finite number | `>=0.001` | 同上 |
| `.boss_element` | enum string | `neutral/metal/wood/water/fire/earth` | 同上 |
| `.skills` | JSON array | 至少 1 个有效技能；`id` 唯一 | 同上 |
| `.resistances` | JSON object | 三个百分比字段均 `0..100` | 同上 |
| `.auto_pill` | JSON object | 完整四字段；目标线不得低于触发线 | 同上 |

`skills[*]`：

| 字段 | 类型/约束 |
| --- | --- |
| `id` | 非空字符串，同境界数组内唯一 |
| `kind` | `damage` / `damage_over_time` / `control` / `output_suppression` |
| `cooldownSeconds` | finite number，`>=0.001` |
| `durationSeconds` | finite number，`>=0.001` 且不大于 cooldown |
| `magnitude` | finite number，`0..1000000000`；具体单位必须在参数元数据中说明 |

`resistances`：

| 字段 | 类型/约束 |
| --- | --- |
| `controlPercent` | finite number，`0..100` |
| `damageOverTimePercent` | finite number，`0..100` |
| `outputSuppressionPercent` | finite number，`0..100` |

`auto_pill`：

| 字段 | 类型/约束 |
| --- | --- |
| `thresholdPercent` | finite number，`0..100` |
| `healPerUse` | finite number，`>=0` |
| `targetPercent` | finite number，`0..100` 且 `>=thresholdPercent` |
| `maxUses` | integer，`>=0` |

### 8.4 待产品/战斗策划决策

- 每个技能 `magnitude` 的单位和不同 `kind` 的解释；当前结构只校验范围。
- 同秒多事件顺序、技能首次施放时点、控制/持续伤害/压制叠加与刷新规则是否采用当前引擎语义。
- 六境界玩家基线档、目标通关时间、自然失败率、丹药消耗和胜率区间。
- 五行、命中、减伤、状态抗性与自动丹药对最终平衡的验收样本。
- 超时上限和失败后的资源/冷却规则是否维持现有状态机。

### 8.5 FI-04 hash 与门禁

- 48 行及 mode 行进入同一新参数版本和 SHA-256。
- `diagnoseHighTierCombatContract` 返回空数组。
- `diagnoseHighTierCombatFormalProvenance` 返回空数组；48 行均为 `frozen_v1`、source 非空，且 source 不含被禁来源词。
- PostgreSQL release lifecycle 的 `validateConfigReleaseSnapshot(...,{requireFormalHighTier:true})` 通过，才能进入 canary/active。
- 六境界固定种子回放、跨配置版本 attempt snapshot、胜负/丹药/技能边界、长期性能和正式平衡报告全部通过。
- `high-tier-full-combat.test.ts` 中的 synthetic fixture 只能作为引擎测试，不是正式发布证据。

## 9. FI-05 法宝阁收藏印记兑换协议包

当前文档描述“10 个印记兑换未拥有法宝”，但正式 API/领域契约未冻结；`CollectionState` 只有全局 `collectionMarks`，不能安全推导境界对象池。不得仅按 proposal 实现。

### 9.1 必须冻结的 API 字段

| 契约项 | 类型/约束 | 待产品决定 |
| --- | --- | --- |
| HTTP route + method | 稳定字符串 | 是否作为 collection action 或独立 exchange route |
| `targetPoolId`/等价语义 | 稳定 enum/string | 首发池与六个高阶境界池如何标识和隔离；字段名需正式冻结 |
| `targetTreasureId`/等价语义 | string 或服务端随机 | 玩家指定目标还是服务端从未拥有/未满星池选择；字段名需冻结 |
| `Idempotency-Key` | header string | 与其他 mutation 一致的 replay 语义 |
| `X-Expected-Revision` | integer header | CAS 冲突规则 |
| response data | object | 消耗印记、获得对象、星级变化、池 ID、剩余印记和审计引用 |

### 9.2 必须冻结的领域规则

- “未拥有”是 0 星还是“未满 10 星”；现有文档存在首发“未拥有”和高阶“未满星”两种口径，必须统一或按池明确区分。
- 全局印记能否跨境界池使用；如果不能，`CollectionState` 需要按池计账和迁移策略。
- 当前池的判定依据、已解锁境界、池全满时行为和印记保留上限。
- 指定兑换与随机兑换的公平性、权重和确定性 seed。
- 并发兑换、重复请求、跨设备冲突、资源不足的原子回滚。
- 旧玩家只有全局 `collectionMarks` 时如何迁移到分池状态。

### 9.3 FI-05 门禁

产品协议批准后，工程必须新增 Schema/DTO 白名单、service mutation、Repository/PostgreSQL 持久化、幂等、CAS、事务、审计和 replay 测试。以下证据全部具备前不能签字：

- 首发池、高阶各境界池隔离 E2E。
- 成功、印记不足、池全满、目标非法、重复请求、并发冲突和事务 rollback。
- 兑换不绕过星级上限、不跨池消费、不产生重复对象状态。
- 新状态字段的版本迁移、历史 snapshot 和进程重启恢复。
