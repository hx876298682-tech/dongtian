# 《洞天》正式输入设计草案：FI-01 / FI-02

> 状态：`proposal_v1`，仅供产品评审。本文不是正式输入包，不得直接驱动运行时，也不得用于生成冻结 CSV、内容 manifest 或 hash。
>
> 本草案只处理普通地图装备内容（FI-01）和清风 30 天装备掉落参数（FI-02）。UI、素材制作、自动升品、随机事件和正式发布版本不在本文冻结范围内。

## 2. FI-01 普通地图内容方案（proposal）

### 2.1 推荐的内容池结构

建议每张地图使用独立的、稳定 ID 的装备模板池，不直接把同一模板隐式复制到另一张地图。这样地图主题、外观、名称和属性模板可以独立演进，掉落回放也能通过模板 ID 复核来源。

建议的最小正式覆盖矩阵如下：

| 地图 | 正权重品质 | 每个正权重品质必须覆盖的六部位 | 最小模板数 |
| --- | --- | --- | ---: |
| 百草谷 | 普通、精良、稀有、史诗 | 6 部位 | 24 |
| 黑风谷 | 普通、精良、稀有、史诗、传说 | 6 部位 | 30 |
| 赤炎洞 | 普通、精良、稀有、史诗、传说、仙器 | 6 部位 | 36 |
| **合计** |  |  | **90** |

90 是满足当前发布门禁的下限，不是内容质量目标。每个矩阵单元至少 1 个模板；产品若希望同一槽位有外观选择，建议每个单元 2 个模板，使总量为 180，并在同一单元内等权或显式配置模板权重。首发 MVP 推荐先采用 90 个稳定模板，避免内容池扩大后又缺少图标和属性验收。

建议 ID 形式为：

```text
equip.<map_id>.<slot>.<quality>.<variant>
```

例如：`equip.bai_cao_valley.weapon.normal.001`、`equip.red_flame_cave.accessory.immortal.001`。ID 一旦发布不可复用；换名、换图标或换属性模板应生成新的内容版本，涉及数值时还应生成参数版本。

### 2.2 内容对象字段建议

当前 `EquipmentTemplate` 只接受 `id`、`display_name`、`slot`、`quality`、`quality_parameter`、`reinforcement` 和可选 `status`。以下是需要产品先同意、再由工程扩展 Schema 的建议字段，不应直接手写到当前 JSON：

| 建议字段 | 建议类型 | proposal 语义 | 必须冻结的问题 |
| --- | --- | --- | --- |
| `name_pool_id` | 稳定字符串，可空 | 首发模板显示名固定；名称池只用于未来实例随机命名，MVP 默认不随机 | 名称是模板固定还是实例随机；名称池是否按地图/品质/部位隔离 |
| `icon_asset_id` | 稳定字符串 | 绑定资源清单中的图标 ID，不允许运行时默认图标 | 资源版本、hash、缺失策略和审核责任人 |
| `appearance_tag_ids` | 非空字符串数组 | 用于外观分类/筛选，不参与掉落概率和战斗数值 | 标签字典、重复标签、是否允许跨地图复用 |
| `stat_template_id` | 稳定字符串 | 引用部位属性比例模板；预算仍由既有品质倍率和槽位预算计算 | 是否允许同部位跨地图复用；属性比例是否只使用当前 V1 模板 |
| `source_map_ids` | 非空字符串数组 | 记录内容来源地图；推荐每张地图独占，若共享必须显式列出 | 是否允许一个模板被多个地图绑定 |

`description`、本地化名称、外观资源和立绘如果进入首发内容包，也必须拥有稳定 ID、审核状态和资源 hash；未完成对象应为 `content_pending`，不得被 map binding 可达。

### 2.3 属性模板建议

产品若没有新的平衡证据，建议先复用当前冻结的槽位比例，不新增地图专属战斗数值：

| 槽位类别 | 普通基础预算 | 攻击占比 | 防御占比 | 生命占比 |
| --- | ---: | ---: | ---: | ---: |
| 武器 | 100 | 70% | 20% | 10% |
| 防具（四槽共用） | 80 | 0% | 70% | 30% |
| 饰品 | 60 | 40% | 40% | 20% |

最终预算仍按 `round(slot_base_budget * quality_multiplier)`，生命按每预算点 `+10` 换算，取整余数回填主属性。速度、五行和特殊词条不从基础预算中扣除，仍按既有品质功能槽规则处理。若产品要让地图装备拥有独立属性比例，必须提交新的 `stat_template_id` 参数来源和平衡复验，不能仅通过内容字段覆盖。

### 2.4 地图 binding 建议

正式内容包中三张地图均需加入非空、无重复的 `equipment_drop.template_ids`。建议 binding 只列出该地图自己的 24/30/36 个模板，并由发布验证器检查：

1. 每个 ID 存在且对象不是 `content_pending`。
2. 每个正权重品质至少有一个模板。
3. 六个实际槽位均至少有一个模板。
4. binding 不跨越未批准的地图主题或版本。
5. 普通/精良自动分解、稀有及以上保留/出售策略与现有 `retain_rare` 契约一致。

### 2.5 名称、图标、外观的首发建议

这是内容制作建议，不是自动生成规则：

- MVP 使用模板固定名称，避免实例命名随机导致回放、仓库筛选和客服定位困难。
- 每个模板一个正式图标；图标 ID 必须指向资源 manifest，缺失直接阻断发布。
- `appearance_tag_ids` 采用稳定枚举，如 `woodland`、`iron`、`flame`、`cloud`，只用于展示和筛选，不改变战斗或掉率。
- 名称池可先登记为 `null` 或 `pending`，但若字段进入正式 Schema，则被掉落 binding 引用的模板不能以 `content_pending` 状态发布。
- 同一模板的显示名、图标、外观标签和属性模板引用必须作为一个内容版本提交，禁止只更新其中一项而不重算 content hash。

## 3. FI-02 清风 30 天参数方案（proposal）

### 3.1 运行口径

冻结的 30 天窗口为 `720h`；现有轮换为高阶远征 `75%`、支援活动 `25%`，所以清风支援时段为 `180h`。清风每场 `600s`，即 `6` 场/h，30 天支援段约 `1,080` 场。装备掉落应在每场独立判定；成功后再从六档品质权重池抽取一次。品质权重是相对权重还是百分比必须写入正式参数元数据，本草案推荐继续使用合计 100 的百分比。

### 3.2 推荐候选值

以下是用于产品评审和敏感性测试的候选值，全部是 `proposal`，不能复制到冻结 CSV：

| parameter_id | 候选值 | unit | proposal 规则 |
| --- | ---: | --- | --- |
| `dungeon.qing_feng.equipment_drop_chance` | **5** | percent | 每场独立装备掉落判定；不继承普通地图或 Boss 掉率 |
| `dungeon.qing_feng.equipment_quality_normal_chance` | **50** | percent weight | 品质池权重 |
| `dungeon.qing_feng.equipment_quality_fine_chance` | **30** | percent weight | 品质池权重 |
| `dungeon.qing_feng.equipment_quality_rare_chance` | **15** | percent weight | 品质池权重 |
| `dungeon.qing_feng.equipment_quality_epic_chance` | **4** | percent weight | 品质池权重 |
| `dungeon.qing_feng.equipment_quality_legendary_chance` | **1** | percent weight | 品质池权重 |
| `dungeon.qing_feng.equipment_quality_immortal_chance` | **0** | percent weight | 保留字段；本候选不掉仙器 |

候选品质权重合计 100，品质期望倍率为：

```text
0.50*1 + 0.30*1.25 + 0.15*1.60 + 0.04*2.10 + 0.01*2.80 = 1.227
```

在 1,080 场期望下，候选结果约为 54 件装备：普通 27、精良 16.2、稀有 8.1、史诗 2.16、传说 0.54、仙器 0。它只是长期均值，不是 30 天保证；固定 seed 结果必须单独报告置信区间和库存出口。

### 3.3 掉率敏感性

在其余条件不变、清风支援 180h 的情况下：

| 总掉率候选 | 30 天期望装备数 | 设计含义 |
| ---: | ---: | --- |
| 3% | 32.4 | 清风更偏资源/法宝，装备成长慢，可能不足以形成六部位重复件 |
| **5%（推荐候选）** | **54.0** | 约每个实际部位 9 件的长期均值，兼顾成型和资源路线定位 |
| 7% | 75.6 | 装备出口和仓库压力明显增大，可能挤压黑风路线差异 |

这张表是敏感性输入，不是最终平衡结论。正式候选至少应以固定 `seed` 集合比较 3/5/7% 三档，而不是只看单个 30 天结果。

### 3.4 清风内容来源 binding

参数与内容必须分开冻结。推荐清风使用“显式的支援路线装备 binding”，内容上复用已经审核的普通地图模板子集，避免复制一套同属性但不同 ID 的装备；参数上仍使用清风自己的一组掉率和品质权重，绝不复用黑风参数。

建议的产品默认：清风绑定每个六部位至少一个普通/精良/稀有/史诗模板，共 24 个模板；若保留传说 1% 权重，则再增加六个传说模板，共 30 个模板。仙器权重为 0 时不需要仙器模板，但 schema 仍保留该参数行并检查非负值。

在工程实现前必须明确以下之一：

- `qing_feng` 绑定普通地图模板的稳定子集，并记录 `template_source_version`；或
- 新增独立清风装备模板对象池，拥有自己的 ID、图标、外观和属性模板。

当前长期运行时只有 `bindingMapId` 概念，不能把清风 route 直接指向普通地图或用空 binding 伪造完成；应先扩展正式内容契约。

## 4. FI-01/FI-02 平衡验收草案

以下是建议的验收门槛，均需产品确认后才能转为正式 release gate：

### 4.1 结构与 provenance

- 所有参数行 `status=frozen_v1`，`source` 指向批准的设计/平衡记录；不得使用本文、`proposal_v1`、fixture 或 synthetic 作为正式来源。
- 新增参数进入同一 CSV 12 列契约，重新生成 frozen parameter 文件和 parameter manifest/hash。
- 内容 Schema 扩展后，content manifest 的 schema/version/hash 与参数 hash 一致；被地图或清风 binding 引用的对象不得为 `content_pending`。
- 三张地图的正权重品质和六部位覆盖全部通过 `validateOrdinaryMapEquipmentRelease` / `diagnoseMapEquipmentReleaseReadiness`。

### 4.2 随机分布

- 普通地图：至少 500 个固定 seed、2,160h，装备总量和六档品质分布均落入 99% 置信区间；三张地图分别核对其冻结期望。
- 清风：至少 500 个固定 seed、720h，报告每个 seed 的清风支援小时、场次、装备总数和品质计数；总掉率和品质权重的观测均值按二项/多项分布计算 99% 区间。
- 不能把均值当保证，也不能只验证品质比例而漏掉清风支援场次数。

### 4.3 经济与出口

- 30 天清风路线必须通过长期运行时 720h 门禁，不返回 `MISSING_PARAMETER`、`INVALID_VALUE` 或 `UNSUPPORTED_POLICY`。
- 记录装备进入仓库、`retain_rare` 出口、普通/精良分解、稀有以上出售和溢出的数量；任何装备不得静默丢失。
- 对 3/5/7% 掉率敏感性候选，比较库存峰值、出售灵石、分解材料、六部位重复件数量和突破资源保留线。
- 清风路线不能凭空产生古修残卷；若产品想让清风独立支付突破，必须另行设计残卷来源或兑换规则。

### 4.4 路线差异

建议把清风定位为“资源/法宝收集优先、装备成长次于黑风”的支援路线。验收时至少比较 30 天和 90 天的：六部位达到精良/稀有的比例、仓库满载率、稀有以上装备出口量、突破支付成功率。若 5% 候选让清风在装备成型上明显超过黑风，应降低掉率或高品质权重；若六部位长期无法达到精良，则重新评审 3%/5%/7% 候选，不得直接改运行时兜底。

## 6. 转正式输入的工程顺序

产品确认后，工程按以下顺序落地：

1. 先更新内容 Schema、对象字段和 binding 契约，补验证器与 content reachability 测试。
2. 生成并审核 90 个以上模板、图标资源 manifest、名称/外观/属性 provenance。
3. 更新清风 7 个参数行和正式 source，生成新的 parameter snapshot/hash；不能手改生成文件。
4. 实现清风 route 的正式内容 binding 和实例生成，接入事务、幂等、CAS、库存出口与审计。
5. 运行普通地图 2,160h、清风 720h/2,160h、多 seed 置信区间及经济敏感性；保存 release artifacts。
6. 只有结构、provenance、hash、随机分布和经济门禁全部通过，才将 FI-01/FI-02 从 `proposal` 改为 `frozen_v1` 并开放运行时。

## 7. 结论

本草案提供了可评审的内容矩阵、字段语义和清风掉落候选，但没有改变当前发布状态。产品确认前，正式 CSV、content JSON、manifest、Schema 和 runtime 都必须保持现状与 fail-closed 行为。
