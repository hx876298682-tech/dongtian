# 《洞天》FI-04 高阶战斗与随机事件正式输入设计草案

> 状态：`proposal_v1`，仅供产品评审和工程拆解。本文不修改 `1.0.0-frozen` 参数包、CSV、生成文件、Schema 或 runtime，也不能作为正式发布 provenance。
>
> 目标：把 FI-04 的 48 个 `full_v1` 字段和随机事件的窗口、抽取、倍率、离线、replay/CAS 语义写成可审批的输入包。产品批准并补充正式来源后，工程才可生成新 config/content version 并实现。

## 1. 当前边界和证据

当前权威参数版本仍为 `1.0.0-frozen`。正式高阶模式是 `signature_only_v1`。`demo/src/server/high-tier-contract.ts` 已有完整模式的结构校验，但权威 CSV 和生成参数没有六境界的 8 类 `full_v1` 字段；测试 fixture 不构成发布证据。

当前已有、但不等于 full_v1 完成的证据：

- 六境界 Boss 生命倍率、签名技能冷却/持续/输出压制和单次丹药预算已经在 CSV 中登记。
- 六境界 `collected_p10` 入口档已有攻击、防御、生命门槛；现有长线联算的自然失败率 `0%` 只适用于该入口档，不代表所有构筑。
- `demo/src/server/high-tier-full-combat.ts` 已有确定性逐秒引擎和 bounded trace，但它使用内存 contract fixture，不能证明正式数值平衡。
- `progress_state.random_event_state` 目前只是 Memory/PostgreSQL 的 opaque JSONB 读写，没有窗口游标、服务器抽取、倍率消费、HTTP DTO 或离线逐窗迁移。
- `docs/洞天随机事件与离线结算V1.md` 仍标记为 `proposal_v1`；其理论公式与 `docs/验证洞天随机事件V1.rb` 的 horizon 截断口径不一致。

## 2. FI-04 产品决策草案

### 2.1 发布原则

1. `full_v1` 只在六境界的 48 个字段全部存在、类型合法、`status=frozen_v1`、`source` 可追溯并通过平衡验收时激活。
2. 任一境界缺字段、技能 ID 重复、技能语义不受当前引擎支持、正式来源缺失或平衡证据缺失，继续使用 `signature_only_v1`；不得填默认值或从三档秘境参数推导。
3. 每境界 8 个字段作为 8 行独立参数登记。`skills`、`resistances`、`auto_pill` 是结构化 JSON 值，不拆成别名字段绕过正式契约。
4. 逐秒战斗在开始时冻结 `combatMode`、境界 contract、玩家 combat snapshot、Boss HP、参数版本和随机种子；settle/replay 只消费快照，不读取当前配置重算。
5. 现有 signature skill 数值作为候选基线保留，不因本草案自动变成正式参数。

表中每一行正好对应 8 个参数，因此共 48 个：

dungeon.high_tier.<realm>.boss_attack
dungeon.high_tier.<realm>.boss_defence

六境界的 `signature_suppression` 候选直接沿用已有签名技能的 `300s` 冷却、`2/3/4/5/6/8s` 持续和 `15/20/25/30/35/40%` 压制边界。`spirit_burn` 只是验证多技能状态机的首轮候选；其伤害单位、叠加/刷新规则和最终值必须由产品批准，不能把普通秘境的 `spirit_burn` 数值直接复用为正式高阶 Boss 技能。

### 2.3 字段语义

`boss_attack`、`boss_defence`、`boss_accuracy` 使用战斗属性 rating；`boss_attack_interval_seconds` 是 Boss 的实际攻击间隔，最小值由 full contract 约束为 `>=0.001`。`boss_element` 使用 `neutral|metal|wood|water|fire|earth`，五行倍率沿用战斗公式的正式版本，不能在技能里再次乘一次。

技能每项必须有：

```json
{
  "id": "signature_suppression",
  "kind": "damage|damage_over_time|control|output_suppression",
  "cooldownSeconds": 300,
  "durationSeconds": 2,
  "magnitude": 15
}
```

产品必须在批准记录中补充以下规则：

- 首次施放是在第 0 秒还是第 1 秒；同一秒多个技能的确定顺序。
- `damage_over_time` 的 `magnitude` 是每秒原始生命伤害还是一次性总量；DoT 是否受玩家 `defence`、五行和 `incomingSpecial` 影响。
- `control` 是否使玩家完全停止攻击；控制重叠是取最大值、相加还是刷新。
- `output_suppression` 是百分比，叠加上限是否为 100%；抗性应用在每次施放时还是每秒生效。
- 技能持续时间是否按对应抗性缩短；当前引擎按施放时冻结持续时间，正式输入需确认该规则。

`resistances` 三字段均为 `0..100` 百分比：

```json
{
  "controlPercent": 25,
  "damageOverTimePercent": 30,
  "outputSuppressionPercent": 20
}
```

`auto_pill` 的 `healPerUse` 以生命值为单位，首轮候选沿用 `combat.pill.heal_per_use=250`；`maxUses` 是一次 Boss encounter 的硬上限，不得越过已登记境界丹药预算。触发线和目标线必须满足 `targetPercent >= thresholdPercent`。丹药不足、达到上限或玩家已死亡时不再补充；成功/失败的资源扣除沿用既有高阶失败契约，除非产品在批准记录中明确改变。

### 2.4 平衡验收门槛

正式输入必须附带可复现的平衡 artifact，而不是只附参数表：

1. 六境界 x 三档秘境 x 固定 100 seed，至少覆盖 `collected_p10`、P25 和 P50 构筑档；保存输入快照、seed 列表、运行器版本、参数 hash 和输出 hash。
2. `collected_p10` 档在三档秘境均不得发生自然失败；入口门槛外的失败必须进入既有失败状态机，不得通过调高 Boss 数值伪造“必胜”。
3. 每境界/秘境的平均通关时间落在该秘境 `target_clear_time` 的 `0.75..1.25` 倍，P95 不超过 `1.5` 倍；若产品要改区间，必须在审批记录给出理由。
4. 丹药消耗 P95 不超过 `auto_pill.maxUses`，并在 720h、2,160h、6,480h 三个 horizon 做净供给守恒；不得把“单次预算”误写成“全局库存”。
5. 对每个技能分别记录触发次数、有效持续秒数、抗性减免量、玩家输出损失、DoT 总伤害、控制秒数、Boss 攻击命中数和失败原因。
6. 相同参数版本、玩家快照、Boss HP、seed 和 attempt ID 的两次模拟必须得到相同 result hash；配置版本变化不能改变已开始 encounter 的结果。
7. 平衡 artifact 通过后才能把 48 行的 `status` 从 `proposal_v1` 改为 `frozen_v1`；没有 artifact 时即使结构校验通过也不得切换 `combat_mode=full_v1`。

## 3. 随机事件正式协议草案

### 3.1 版本和参数

建议新增独立的 `random_event_runtime_v1` 语义版本。当前 CSV 的数值可作为首轮候选，但不因本节自动改变为正式玩法：

| 参数 | 当前候选 |
| --- | ---: |
| 窗口 `roll_interval_hours` | 168h |
| 同时活动上限 `max_active` | 1 |
| `spirit_tide` 概率/持续/倍率 | 20% / 6h / 1.25x |
| `beast_raid` 概率/持续/倍率 | 10% / 4h / 0.80x |
| 未触发 | 70% / 168h / 1.00x |

窗口按 UTC 服务器时间锚定：

```text
windowId = floor(unixSeconds / 604800)
windowStart = windowId * 604800
windowEnd = windowStart + 604800
```

窗口边界和客户端时区无关。每个玩家每个窗口恰好一次服务器抽取；同一窗口不能重抽、叠加或因客户端重试改变结果。

### 3.2 抽取与状态

抽取使用服务器侧随机源，客户端不得提交 roll。随机源必须在事务中取值并持久化 `drawIndex`/`roll`；若采用确定性派生随机，则必须固定算法、密钥版本和 canonical input。无论采用哪种实现，回放只读取已保存的 roll，不重新抽取。

建议把当前 opaque JSONB 迁移为以下受版本保护的对象；正式工程实现可以把窗口记录拆到表中，但语义不能减少：

```json
{
  "schemaVersion": "random_event_runtime_v1",
  "settledThrough": "2026-08-26T00:00:00.000Z",
  "activeWindowId": "2944",
  "windows": [
    {
      "windowId": "2944",
      "startAt": "2026-08-24T00:00:00.000Z",
      "endAt": "2026-08-31T00:00:00.000Z",
      "roll": 12.345678,
      "eventId": "spirit_tide",
      "status": "active",
      "durationSeconds": 21600,
      "productionMultiplier": 1.25,
      "configVersion": "random-event-approved-version",
      "drawIndex": 4,
      "resultHash": "sha256:..."
    }
  ]
}
```

`eventId` 只能是 `none|spirit_tide|beast_raid`；窗口记录的 `status` 只能是 `rolled|active|ended`。`none` 窗口也必须保存记录，以证明该窗口已经抽过。`activeWindowId` 和 `settledThrough` 是派生/游标字段，必须与 `windows` 校验一致。至少保留覆盖最近 24 小时结算上限加一个完整窗口的记录；正式审计/回放记录不能仅依赖会被裁剪的 JSONB，建议增加不可变 `random_event_window` 事件表或审计事件流。

抽取顺序固定为半开区间 `[0,100)`：

```text
0 <= roll < 20       -> spirit_tide
20 <= roll < 30      -> beast_raid
30 <= roll < 100     -> none
```

这明确采用当前 Ruby 脚本的互斥、按顺序抽取口径；不能把两个概率当成可同时命中的独立事件。

### 3.3 倍率消费

- 随机事件倍率只作用于生产动作，不作用于战斗伤害、秘境掉落、高阶远征供给、保底和突破成本。
- 生产结算按动作时间与事件活动区间的重叠秒数积分；跨窗口或跨事件时拆成区间后求和，不能按“动作完成时刻”整段套倍率。
- 事件持续结束后立即恢复 `1.00x`，不把未使用时长转成库存，也不产生负库存。
- 在线和离线使用同一套时间积分；离线不是必得事件，也不把概率转成保底。
- 已开始但尚未完成的生产动作使用其实际重叠区间；不得因登录/登出把整个动作改判为在线或离线倍率。

### 3.4 离线跨窗和激活迁移

离线结算继续遵守单次最多 24 小时。结算区间按服务器时间截断后，按窗口从旧到新逐窗处理：

1. 为每个相交窗口补齐且只补齐一条 `rolled` 记录。
2. 读取记录中的 event、倍率和 config snapshot，计算该窗口与生产动作的重叠。
3. 结束窗口后更新 `status=ended`、`settledThrough` 和玩家 `state_revision`。
4. 所有资源、动作余数、随机事件状态、随机计数器和 settlement record 在同一事务提交。

激活 `random_event_runtime_v1` 时，旧玩家只有 opaque/空 JSONB，无法安全推断历史 roll。建议迁移策略为：以玩家 `lastSettledAt` 所在窗口初始化游标，激活前窗口统一记为 `none` 且不补发历史倍率；从下一个未结算窗口开始抽取。若产品要求追溯历史，必须提供服务器历史随机源/窗口账本，否则应拒绝迁移而不是用当前配置重算。

若某窗口使用的历史 config snapshot 已被删除，离线结算必须 fail-closed 并报警，不能用当前版本替代。建议 release registry 至少保留覆盖最长离线窗口、当前活动窗口和 replay 保留期的随机事件快照。

### 3.5 Replay、CAS 和 API DTO

随机事件不提供客户端“重抽” mutation。建议 API 只有：

```text
GET  /v1/random-events/current
POST /v1/settle                 # 在既有离线结算响应中返回 randomEvents
```

`GET /v1/random-events/current` 返回：

```json
{
  "configVersion": "...",
  "serverNow": "...",
  "windowId": "2944",
  "windowStartAt": "...",
  "windowEndAt": "...",
  "status": "active|ended",
  "eventId": "none|spirit_tide|beast_raid",
  "productionMultiplier": 1.25,
  "stateRevision": 7
}
```

客户端不能提交 `eventId`、`roll`、`productionMultiplier` 或 `windowId` 作为事实来源。`POST /v1/settle` 的响应应带每个已处理窗口的只读摘要：`windowId`、`eventId`、重叠秒数、倍率、configVersion 和 `resultHash`。

幂等规则：

- 同一 `settlementId` 已 `committed`：返回第一次响应，不能重新抽取、重复生产或推进游标。
- 同一 `settlementId` 为 `pending`：按既有 settlement 恢复/拒绝规则处理，不能创建第二条窗口记录。
- 新请求必须携带 `expectedRevision`；不匹配返回 `STALE_REVISION`，不写任何状态。
- 同一玩家同一 `windowId` 必须有唯一约束/事务 guard；重复窗口插入返回原记录。
- 事务失败时资源、动作余数、窗口记录、随机计数器和审计事件全部回滚。
- replay 以 `settlementId + configVersion + input snapshot hash` 校验；结果 hash 不一致视为数据损坏并 fail-closed。

## 4. 随机事件公式冲突及处理意见

现有文档写出的 `1.002976...` 与其正文公式本身不一致；按 `20%/6h/1.25x` 和 `10%/4h/0.80x` 的完整 168h 窗口，正确期望是：

```text
1 + (0.20 * 6 * 0.25 + 0.10 * 4 * -0.20) / 168
= 1.0013095238...
```

现有 Ruby 验证器针对 `horizon=2160h` 使用 `floor(2160/168)=12` 个完整窗口，正确的截断期望是：

```text
E(H) = 1 + floor(H / interval) / H
             * sum(chance_i * duration_i * (multiplier_i - 1))
E(2160) = 1.0012222222...
```

当前脚本输出 `expected_production_factor=1.001222`、`mean=1.001222`、`ci99=+/-4.0e-05`，因此脚本结果与“12 个窗口截断 horizon”一致，但与文档的 `1.002976...` 不一致。正式输入前必须由产品批准一个 canonical 口径：

- 统计样本是否只包含完整窗口；
- 非整窗 horizon 的分母是完整窗口时长还是实际 horizon；
- 部分窗口事件持续时间是否按真实重叠秒数计入；
- 99% CI 的 seed 范围、样本数、置信区间算法和舍入规则。

本草案建议采用上面的 `E(H)`，并把完整窗口基线 `1.0013095238...` 与 `2160h` 截断基线 `1.0012222222...` 同时写入验证 artifact。未完成口径批准前，不修公式、不接入 runtime、不把随机事件标记为正式完成。

## 5. 正式输入提交和工程验收清单

产品批准后提交：

1. 六境界 48 行参数：每行 `status=frozen_v1`、非空正式 `source`、单位、公式/规则、舍入和批准记录。
2. full_v1 技能语义表：首次施放、同秒顺序、控制/DoT/压制叠加、抗性时点、自动丹药和失败边界。
3. 六境界平衡 artifact：固定 seed、入口档、通关时间、失败率、丹药消耗、长期供给、输入/输出 hash。
4. `random_event_runtime_v1` 参数与 state schema、UTC 窗口锚点、随机源/密钥版本、历史 snapshot 保留期、激活迁移决定。
5. 随机事件公式修订和 5,000 seed/2,160h 验证 artifact；文档公式与 Ruby 验证器必须同一口径。
6. route/DTO、settlement replay/CAS、唯一窗口记录、审计事件和离线跨窗验收用例。

工程收到上述批准输入后，按以下顺序实施：Schema/参数包 -> manifest/hash/provenance -> full_v1 runtime 和随机事件 runtime -> Memory/PostgreSQL/CAS/幂等 -> focused/全量/真实 PostgreSQL/Ruby 审计 -> release gate。UI 仍最后处理。

## 6. 当前结论

这份文档只完成“待产品审批的正式输入设计”，没有关闭 FI-04 或随机事件阻断。当前 release 继续使用 `signature_only_v1`；随机事件继续作为 `proposal_v1 + opaque JSONB`。任何将本草案候选值直接写入 CSV、生成参数或激活 runtime 的操作，都不满足现有发布门禁和 provenance 要求。
